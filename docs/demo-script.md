# 视频演示手册（逐镜头台词稿）

> 目标：3–4 分钟成片。录屏 + 口播（或后期配音）。
> 录制前检查：服务 `:8090` 运行、`kubectl` 可连 makejob 集群、浏览器打开两个标签页（智能助手 + NOC 大屏）、终端字体 ≥20px、OBS 已开录制。
>
> **两条铁律**：①先完整彩排一遍再正式录；②LLM 推理等待段全部后期加速，不要现场干等。

## 镜头 1 · 开场（NOC 大屏）

**画面**：`/noc` 全屏，F11。
**台词**：
> "好的，上一p我们讲解了prehire这个求职辅助平台的功能。接下来这个系统，是专门运维它的多智能体 AIOps：告警会自动创建工单，多个 Agent 协作完成根因定位，产出带证据引用的事故报告。大家看到的所有数据，都来自这个集群里真实运行的 Prometheus——不是 mock。"

**预期画面**：16 个服务全部绿点、5xx 速率 0.000、P99 曲线平稳、LIVE 红点闪烁。

## 镜头 2 · 制造故障（终端）

**前置命令**（录制前新开终端，准备好直接回车）：
```bash
kubectl scale deployment makejob-question --replicas=0
```
```bash
for i in $(seq 1 300); do curl -s -o /dev/null -m 3 http://localhost:8080/api/v1/questions; sleep 0.5; done
```
> ⚠️ 第二条是 2.5 分钟的流量循环，**切到下个镜头前先启动它**（回车后立刻 Alt+Tab）。

**台词**：
> "现在我来制造一次真实故障：把 question 服务缩容到零副本——相当于线上事故里最常见的服务宕机。同时用脚本持续请求网关，模拟用户流量。"

**预期画面**：终端显示 scaled；流量循环开始刷屏（无输出）。

**预期画面**：5xx 速率卡从 0.000 涨到 1.0+；5xx 曲线抬头；LIVE 红点闪烁。

**台词**：

**预期画面**：新会话出现在左侧列表；意图识别消息出现（类型=5xx_surge）；「多 Agent 处理中」状态点亮。

## 镜头 6 · 事故报告（同页面）

**画面**：报告卡已弹出，**滚动展示各区块**：置信度仪表环 → 根因 → 时间线（点开一个证据徽标）→ 处置建议。
**台词**：
> "这是自动生成的事故报告：置信度 0.85，根因指向 question 服务不可用导致网关 500。每条结论都挂着证据引用——点开就能看到当时查询的真实 Prometheus 数据，**结论必须有证据支撑，这是我们对幻觉的硬约束**。下面是分级处置建议：高危的需要人工确认。"

**预期画面**：报告卡完整；点击证据徽标弹出抽屉显示原始 JSON；HypothesisFlow 显示 confirmed/rejected 状态。

## 镜头 7 · 发起处置（详情页 + 终端）

**画面**：点报告卡上「查看完整报告 / 执行处置 →」进详情页，滚到处置建议，点「发起处置」→ 确认对话框 → 「创建待审批 CR」。
**同时**：切终端开一个窗口跑：
```bash
kubectl get remediations -w
```
**台词**：
> "注意，处置不是点击就完事——点「发起处置」会把建议物化成一个 Kubernetes CR，Remediation。它的状态现在是 PendingApproval，等待人工审批。审批人身份、执行结果、恢复回验，全部写在这个 CR 的 status 里——这就是把运维处置做成平台 API。"

**预期画面**：对话框 → 成功消息「处置 CR 已创建，等待人工审批」；终端 `kubectl get remediations -w` 出现一行 `rem-t-…`，PHASE=PendingApproval；详情页出现「处置审批」表格。

## 镜头 7B · 人工审批门 → Operator 执行 → 自动回验（详情页 + 终端）

**画面**：详情页「处置审批」表格点「审批」→ 确认；切终端看 `-w` 输出滚动。
**台词**：
> "现在我来审批——这里我签的是我的身份，会写进 CR 可追溯。审批通过后，operator 马上认领执行权：PendingApproval → Executing → Verifying。它不是 sleep 完事，而是等观察窗后查真实 Prometheus 指标做恢复回验；回验通过 CR 变 Succeeded，工单自动关闭。整个状态机是 level-triggered 的——现在我可以把 operator 重启甚至杀掉 leader，重启后它从 status 断点续跑，绝不会重复执行变更。"

**预期画面**：`-w` 依次翻过 `PendingApproval → Executing → Verifying → Succeeded`；`kubectl describe remediation rem-…` 可见 Events 时间线；详情页消息流出现 🛠️ Remediation 阶段消息；工单状态变绿「已解决」。
**彩排要点**：双副本 operator 演示「杀 leader 不双执行」：`kubectl delete pod -l app=aiops-operator` 后观察另一副本接管，Verifying 阶段续跑。
**兜底**：若 operator 链路现场异常，手动 `kubectl scale deployment makejob-question --replicas=1` 后，CR 回验依然会通过并自动关单（回验只看真实指标，不关心谁修的）——这本身就是一句好台词。

# 故障与恢复命令速查

| 动作 | 命令 |
|---|---|
| 注入 5xx 故障 | `kubectl scale deployment makejob-question --replicas=0` |
| 制造流量 | `for i in $(seq 1 300); do curl -s -o /dev/null -m 3 http://localhost:8080/api/v1/questions; sleep 0.5; done` |
| 手动恢复 | `kubectl scale deployment makejob-question --replicas=1` |
| 验证恢复 | `curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/api/v1/questions`（200 即恢复；首次可能 500，gRPC 重连约 1 分钟） |
| OOM 故障 | `kubectl run oom-demo --image=busybox:1.36 --restart=Never --limits=memory=16Mi -- /bin/sh -c "dd if=/dev/zero of=/dev/shm bs=1M count=64"` |
| 慢查询故障 | `docker exec aiops-postgres psql -U aiops -d aiops -c "SELECT pg_sleep(600)" &` |
| 清理演示资源 | `kubectl delete pod oom-demo --ignore-not-found` |
| 观察处置全链 | `kubectl get remediations -w`（PHASE: PendingApproval→Executing→Verifying→Succeeded） |
| 处置时间线 | `kubectl describe remediation rem-<工单号>`（Events 含审批/执行/回验全过程） |
| operator 双副本 | `kubectl get pods -l app=aiops-operator`（leader election；杀 leader 后另一副本接管续跑） |

# “能不能让系统自己修好？”

**能——这正是 P4 已实现并验收过的能力**，但注意边界：

- 系统**自动做**的：故障定位 → 报告 → **复查 5xx 是否回落 → 自动关单**。也就是说：您（或告警）建单后，只要故障被修复，关单是全自动的。
- **扩容/回滚这类变更操作**需要人工确认——这是刻意设计（高危操作必须有人的签字），视频里镜头 7 那一下点击就是演示重点。
- 如果您想让**系统连扩容都自动做**：技术上把 P4 复查通过后自动对 P0 级工单执行建议动作即可实现，但演示时保留“人工确认”那一秒，恰恰是展示“高危操作有人机边界”的正确姿势——这是面试官会认可的运维价值观。

所以推荐的演示姿势：**镜头 7 那一次点击，是全场唯一的人工介入**——让它留在视频里，这就是故事的高潮。
